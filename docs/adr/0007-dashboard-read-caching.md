# ADR 0007: Dashboard read caching — in-process + Next.js, not the query layer

## Status

Accepted — 2026-07-15. **Amended by ADR 0013 (2026-09-09):** the caching design stands, but the cross-edition reasoning below is moot — there is one bot, so `cachedGet` takes no edition, nothing is "shared across editions", and the pending-handover cross-edition read it optimised no longer exists. `healAbsentEditions` is now `healAbsentGuild` (one guild, one bot, no entitlement gate on the heal).

## Context

The dashboard "feels slow to use," worst on the **cold first load** of a guild page. Tracing both read endpoints showed the wall-clock cost is **Discord-REST-bound, not Postgres-bound**:

- `GET /api/guild/:guildId` makes up to **8–9 Discord REST calls** for a legacy guild with a pending handover (channels, roles, bot member, per-channel permission math — plus, before this ADR, a duplicate `GET /guilds/:id/channels` in handover eval), each ~150–300ms through the proxy. The 3–4 Postgres queries total ~20–50ms.
- `GET /api/user/guilds` is 1 Discord call + 3 sequential Postgres queries (+ presence-heal Discord checks only when a presence row is absent).
- The web layer had **no caching at all**: every navigation re-fetched cold.

A query-result cache (e.g. Drizzle's `$withCache`) was the initial idea. It is the wrong tool here on two counts: (1) it caches the backend's own `db.select()` reads, which are <10% of the latency; (2) it cannot serve the bot's hot-path caches (`Channels`, `MigratedGuilds`) — the bot reads Redis directly by explicit key and never runs Drizzle, so a query-hash-keyed cache is unreachable from it. It would delete ~0 lines and move the needle ~0%.

## Decision

Diagnose the felt slowness as Discord-REST cost + zero web caching, and fix it in the layers where the work actually happens. **Do not add a query-result cache.** The design has four parts: a structural dedup, a backend in-memory Discord-response cache (with stale-while-error), a targeted invalidation policy, and the web-layer data-flow (no server-side payload cache, RSC-seeded client provider, streamed detail).

### Lever A — structural dedup (carries the cold load)

- Handover eval receives the already-fetched channel list instead of re-fetching `GET /guilds/:id/channels`.
- The dependent branches (legacy-perms recompute, handover eval) run in parallel — both depend only on the prior batch — and the sequential Postgres reads are parallelized/collapsed.
- **Cross-endpoint `/users/@me/guilds` dedup.** Within a single guild-page load the layout calls `getUserGuilds()` (`GET /api/user/guilds`) and `getGuildDashboard()` (`GET /api/guild/:guildId`), and the latter's `requireGuildPermission` middleware makes its **own** `/users/@me/guilds` fetch to check `MANAGE_GUILD`. These are two separate web→backend requests, so React `cache()` can never dedup them (the middleware's fetch runs in the backend, out of React's reach — this is why the originally-planned `cache()` wrap on `getUserGuilds()` was a no-op and was dropped). Instead, `GET /api/user/guilds` **reads through and warms** the same per-token cache key the middleware reads (`discordGuildsCacheKey(token)` → `discord_guilds:{tokenHash}`, `DiscordAuth` Redis DB, 60s TTL, via the shared `discordGuildsCacheKey()` / `GUILDS_CACHE_TTL_SECONDS` from `@ap/express`). Because the layout awaits `getUserGuilds()` before `getGuildDashboard()`, the middleware read-hits the warm entry and skips its Discord call entirely. This call is on the _user's_ OAuth token, direct to Discord (**not** through a proxy), so it never counted toward the Cloudflare invalid-request budget — the win is latency + user-token rate-limit headroom, not bot budget.

### Lever B — backend in-memory Discord-response cache

`Discord.cachedGet(route)` (`apps/backend/src/services/discord.ts`) caches the raw responses of the three per-guild bot-scoped GETs — `/guilds/:id/channels`, `/guilds/:id/roles`, `/guilds/:id/members/:botId`.

- **Keyed by route only, 5-min fresh TTL.** `/channels` and `/roles` are guild-global (Discord returns all channels/roles regardless of the fetching bot's permissions — confirmed in the Discord docs), so a single entry per guild is shared across editions; the free bot's fetch during a pending handover warms the cache for the premium bot's permission eval. `/members/:botId` self-namespaces by `botId`, so editions never collide.
- **Invariants:** a miss is fetched via an edition whose bot is **present** in the guild (a non-member gets 404/403), and **only 200 responses are cached** — a stray error never poisons the shared key.
- **Stale-while-error (last-known-good).** Alongside the 5-min fresh cache, `cachedGet` keeps a second, long-lived **last-known-good** store (`lastKnownGood`, 1h TTL). On success it writes both caches (LKG holds only 200s, same invariant). On **any** thrown error it returns the last-known-good value for that route if present (warn-logged), rethrowing only when there is no prior good value. This exists because `GET /api/guild/:guildId` has two blocking dependencies through `cachedGet` (`fetchAnnouncementChannels` → `/channels`, and `getPublishMap` → `/roles` + `/members`), so any momentary Discord/proxy blip on a cold read otherwise became an uncaught throw → generic 500 (`@discordjs/rest` errors expose `.status`, not `.statusCode`, so `getErrorStatusCode` collapses them) → the web layout's `TRANSIENT_ERROR` → the "Guild detail temporarily unavailable" card. Serving last-known-good turns that blip into a 200 with a full, name-intact list.
  - **Serve stale on ANY error, not just classified-transient.** Genuine bot-absence is owned upstream by the presence layer — kick/leave soft-deletes presence, and the detail handler's `healAbsentEditions` does a live `isBotInGuild` recheck that throws `409 BOT_NOT_PRESENT` _before_ `fetchAnnouncementChannels` runs. So a 403/404 at the channel fetch can only be a seconds-long kick race that self-heals — not worth classifying error shapes inside `cachedGet` or reintroducing a throw→500→card path.
  - **1h LKG TTL** covers the dominant "return to a guild after the 5-min fresh TTL lapsed, first read is cold + blips" case while capping worst-case fallback staleness at something a user won't find bizarre.
- **In-memory, not Redis.** The backend is a single instance (ADR 0006), and the TTL caches self-evict, so they stay small and bounded — putting them in Redis would grow the instance for no benefit. The cache uses a small hand-rolled `createTtlCache<T>()` helper (Map + `expiresAt` lazy expiry + size-gated prune) matching the backend idiom — no new dependency, no LRU cap needed. The other ad-hoc in-memory caches (`getBotUserId`, subscriber-username, presence-heal negative cache) share the same helper.
- **Explicit opt-in.** `cachedGet` is used only at the guild-dashboard read call sites — **not** a transparent wrapper over `restFor().get()`. Presence-heal's `isBotInGuild` (same `/members/:botId` route) must keep calling live, or a stale cached member would report a departed bot as present and break absence detection.
- **`LegacyGuildPerms` (Redis DB 7) is retired.** Once raw `/roles` + `/members` are cached, recomputing the legacy-guild `canPublish` map is pure in-memory math, so the dedicated cache and its `services/legacyPerms.ts` are deleted. DB 7 is now unused.
- The composed endpoint still reads Postgres (channels/filters/subscription) and Redis (handover marker, publish-state) **live**, so dashboard mutations reflect instantly — only the slow, rarely-changing Discord data is cached.

### Cache invalidation

**Permission data is TTL-only; channel-list membership is actively evicted; a fetch error falls back to last-known-good.**

- **Permissions (roles, bot member, `canPublish`) stay TTL-only (5 min).** Active eviction on permission-change pings (`roleUpdate` / `guildMemberUpdate` / `channelUpdate`) is rejected: member/role/overwrite churn is high-frequency in busy guilds, so eviction would fire constantly and pay near-full Discord cost on every load — burning the invalid-request budget exactly where it is scarcest. The 5-min bound is the ceiling on permission staleness.
- **The channel list (`/guilds/:id/channels`) is actively evicted on a membership change** — which channels _exist_ and their types, a distinct dimension from permission freshness. A freshly created announcement channel would otherwise be invisible for up to 5 min; a deleted or announcement→text-demoted one lingers as a phantom candidate. Membership changes are rare (unlike permission churn), so eviction is cheap. Eviction fires when the bot observes: `channelCreate` (announcement), `channelDelete` (announcement), and `channelUpdate` **only when the type crosses the `GuildAnnouncement` boundary** (either direction).
  - **Transport:** `POST /internal/guild/:guildId/channels/invalidate` → `Discord.evictGuildChannels(guildId)` (`discordReadCache.delete(Routes.guildChannels(guildId))`). Guild-scoped because eviction must fire even for channels with no registered `channel` row. Deliberately **not** folded into the permission-sync path (`syncChannels` / `POST /internal/channel-permissions/:guildId`), which is also called by the high-churn `guildMemberUpdate` / `roleUpdate` pings — piggybacking there would silently re-introduce the rejected permission-eviction behavior.
  - **Membership, not metadata.** Eviction never fires on rename or reposition, even though channel names and `position` live in the same cached blob and are therefore ≤5 min stale. A wrong name/order is cosmetic; a missing/phantom channel is a real breakage. Rename/move are also higher-frequency, so evicting on them would creep back toward the churn this ADR rejects.
  - **Seed on create.** `channelCreate` also pushes publish-state (`syncChannels(full:false, clearBlocked:false)`): the bot computes `canPublish` for free from the `CHANNEL_CREATE` payload's `permission_overwrites`, so the new channel's first dashboard read hits a warm publish-state entry instead of a Discord REST write-back (ADR 0008).
  - **Re-invite eviction (absent-window gap).** While no edition's bot is in the guild, Discord fires no gateway event, so a channel created/deleted during that window is never invalidated. `registerNewGuild` (the `guildCreate` re-invite path) therefore calls `Discord.evictGuildChannels(guildId)` unconditionally right after `activatePresence` — the exact point a present bot is confirmed — placed **before** `Handover.evaluate` (which reads the same entry) so the eval runs on fresh data. Evicting on re-invite rather than on kick is sufficient: nothing can re-warm the entry with stale data while absent (a refetch needs a member bot; a non-member's fetch 403s and only 200s are cached), and re-invite eviction is backend-internal (no bot round-trip).
- **A fetch error serves last-known-good** (Lever B, up to 1h) rather than propagating — `lastKnownGood` is **not** cleared by `evictGuildChannels`/`evictGuildRoles`, because eviction forces a fresh fetch for correctness and the stale value only surfaces if that fresh fetch itself fails.

### Guild-list read path + presence self-heal

- **`GET /api/user/guilds` reads through its own cache** (the same 60s per-token `DiscordAuth` key, see Lever A): it reads the key first and skips the Discord `/users/@me/guilds` fetch on a hit. Presence/subscription are still composed live from Postgres every call, so only the raw user-token list read is cached — no staleness in the derived flags.
- **Presence self-heal is per-guild, entitlement-gated — not a list-wide fan-out.** Healing every managed guild whose presence row looked absent was an O(admin-guild-count) spray of `isBotInGuild` on every dashboard load, mostly re-confirming permanent, correct absences (the premium bot legitimately not in a free-only guild, etc.). That fan-out is deleted. Heal now fires only on `GET /api/guild/:guildId` (the one guild it serves), and its premium check is entitlement-gated (`!!sub && isEntitledStatus(sub.status)`) — a non-entitled guild's only "present" outcome is the revocation leave (`joinRails`), already owned by the nightly reconcile. Authorization + presence gating for a guild page live entirely on the detail endpoint (`requireGuildPermission` + a botless-guild throw), so the `[guildId]` layout does not fetch the guild list to gate — it renders and lets the detail read decide.

### Web layer — no server-side payload cache; RSC-seeded provider; streamed detail

- **No cross-request Next.js Data Cache for the guild payload.** Authorization for `/api/guild/:guildId` is per-user and enforced **in the backend** (`requireGuildPermission` checks `MANAGE_GUILD`, 60s-cached per token); the web's `auth()` only checks that the user is logged in. Caching the composed payload in the shared server-side Data Cache would let a cache hit short-circuit the backend call, serving a guild's data to any logged-in user who navigates to `/dashboard/{guildId}` without the `MANAGE_GUILD` gate ever running — an authorization bypass. So every guild load hits the backend and authorization runs every time. Warm navigation is still fast because Lever B serves the Discord data from memory and the 60s per-token authz cache makes the permission check nearly free (~50–150ms warm vs. ~600ms cold).
- **Instant back-navigation** to an already-opened guild comes from Next.js's **client Router Cache** (`experimental.staleTimes.dynamic = 60`; default 0 = refetch every navigation). Per-browser (no cross-user exposure), and the mutations' existing `router.refresh()` busts it so edits still reflect immediately; `useRefreshOnReturn` keeps the guild list fresh after an invite.
- **RSC-seeded client guild-list provider.** The guild list is fetched once in the shared `dashboard/layout` (server) and seeded into a pass-through **client** context (`GuildListProvider`, `components/dashboard/guild-list-context.tsx`, no browser storage — the server re-seeds on every hard load, Next's layout persistence keeps it mounted across nested navigation, revalidated by `router.refresh()` on mutations + the post-invite focus handler). The chrome (switcher + tab links) renders **outside** the detail `<Suspense>` from that provider + the route param, so switching guilds keeps the switcher instant; only the main content shows a loading state. The guild-detail payload is **streamed as a promise** consumed with React 19 `use()`, so only the main content and the attention badge suspend. The post-invite focus handler refreshes the list and navigates into the invited guild **only once its bot shows present** in the fresh list — never into a still-botless guild (which would bounce with a Discord "Missing Access"); otherwise the user stays on the refreshed server list.
- **Full client-side data-fetching (SWR / React Query) is rejected — on security grounds, not just cost.** The browser never touches the backend today: reads run in Server Components, mutations are Server Actions, and `backendFetch` is `server-only` (it attaches the Discord token server-side and calls the private `BACKEND_URL`). Moving fetches client-side would either expose `BACKEND_URL` + require a browser-held credential (a DDoS + token-exposure surface) or demand a new BFF route layer that doesn't exist — a net complexity add. The RSC-seeded provider delivers the instant-switcher win within the existing server-component model, with no new browser-facing surface.
- The frontend also has a silent auto-retry boundary around the streamed detail (`guild-detail-boundary.tsx`) as a last-resort backstop for the residual case Lever B's stale-while-error cannot turn into a 200 (the backend/proxy itself briefly unreachable): a transient failure retries under the ordinary loading skeleton for ~10s before ever showing the manual retry card (see ADR 0010 for the auth/transient signal taxonomy).

## Alternatives considered

- **Drizzle `$withCache` / query-result cache** — targets Postgres reads (<10% of latency) and cannot serve the bot's direct-Redis hot-path caches; deletes no code, fixes nothing felt. Rejected.
- **Cache in Redis instead of in-process** — unnecessary for a single-instance backend and works against the standing goal of keeping Redis from growing; a self-evicting TTL cache doesn't need cross-process durability. Rejected (revisit only if the backend goes horizontal — correctness holds either way, only hit rate drops).
- **Coarse whole-payload cache** (cache the composed `getGuildDashboard` result, TTL) — simplest, one key, but a TTL over DB-sourced state delays channel/filter mutations by up to the TTL, relocating "slow to use" onto writes. Rejected; the fine-grained split keeps mutations instant.
- **Next.js Data Cache on the composed guild payload** (`revalidateTag` + `revalidate`) — would speed navigation, but the shared server-side cache sits _in front of_ the backend's per-user `MANAGE_GUILD` authorization → authorization bypass (see Web layer). Making it safe requires a per-user authz gate on every request, eroding the benefit. Rejected in favor of hitting the backend live.
- **Active eviction on permission-change pings** (`roleUpdate` / `guildMemberUpdate` / `channelUpdate` for permissions) — fresher permission data, but busy guilds would evict constantly and pay near-full Discord cost on every load, burning the invalid-request budget where it is scarcest. Rejected in favor of the 5-min bound. (Channel-list _membership_ eviction is a separate, low-frequency case and is accepted — see Cache invalidation.)

## Consequences

- Net **fewer Discord REST calls**: Lever A removes the duplicate channel fetch and the cross-endpoint guild-list refetch; Lever B collapses repeat/concurrent loads and pending-handover cross-edition reads to cache hits. This is the primary win and aligns with the standing REST-budget discipline. Cold first load drops from ~8–9 serial Discord calls to ~4–5 in two parallel batches.
- **Staleness contract:** everything the user edits in the dashboard (enabled channels, filters, subscription, migration, pending) reflects **immediately** (read live from Postgres/Redis every request). Permission-derived Discord data (roles, bot member, `canPublish`) is up to 5 min stale. The channel-list _membership_ reflects changes within seconds (active eviction). On a live-fetch error the read serves last-known-good (up to 1h) rather than failing — happy-path reads are unaffected (LKG only serves on a thrown fetch).
- Redis DB 7 (`LegacyGuildPerms`) and `services/legacyPerms.ts` are deleted; the legacy `canPublish` map recomputes from the in-memory Discord cache.
- No shared web-layer payload cache means no `revalidateTag` wiring to maintain in mutation paths. Instant back-navigation is the one-line `staleTimes.dynamic = 60` (client Router Cache, per-browser, busted by `router.refresh()`), not a client-caching library. Authorization runs on every guild load.
- The backend cache is per-process; a future horizontal scale-out lowers hit rate but never correctness.
