# Domain language

Concepts that show up across the codebase. Keep this list short — only terms that mean something specific to maintainers, not generic web/Discord terms.

## Crosspost pipeline

- **Crosspost** — Discord's "publish" action on an announcement-channel message. Limited to 10/hour/channel by Discord.
- **Proxy** — single service that owns all Discord REST traffic. Two responsibilities: (1) async crosspost queue with `POST /crosspost/:c/:m` (ACK in <100ms), (2) generic Discord REST passthrough at `/api/*` used by the bot's discord.js. Single `@discordjs/rest` instance shared by both paths; `BurstHandler` lets interactions bypass the crosspost queue naturally.
- **Gate** — synchronous pre-checks the proxy runs before queueing or processing a crosspost. Order: `invalid_requests` (system shed) → `blocked` (cached denylist) → `sublimit` (per-channel 10/hr counter).
- **Sublimit** — Discord's per-channel 10/hour crosspost limit. Mirrored as a Redis counter (`SublimitCounter` DB). Different from a regular route 429.
- **Blocked channel** — a channel where Discord refused crosspost with 401/403 (missing permission, channel deleted). Cached in `BlockedChannels` Redis DB with 1h TTL. Bot can `DELETE /internal/blocked/:c` to clear when permissions are restored.
- **Invalid request budget** — Cloudflare bans an IP after 10k 401/403/non-shared-429s in 10 min. Proxy self-sheds at 5k to stay well under. Tracked in-memory in the proxy (not Redis); counter sourced from `@discordjs/rest`'s `RESTEvents.Response` event, filtered to exclude shared 429s per Discord docs.
- **Passthrough** — proxy's `/api/*` route that forwards generic Discord REST calls on behalf of the bot. Selective header forwarding (`Content-Type`, `x-audit-log-reason`); body forwarded only when `content-length > 0` or `transfer-encoding` is set.
- **Onboarding boost** — a newly-joined guild's first 10 **successful publishes** jump the queue, so a new admin sees the product work instead of watching their first message sit behind the peak backlog (~3000 waiting jobs, minutes to an hour). Budget lives in `boost:{guildId}` (DB 14, integer remaining, 90-day safety TTL); **key presence is the boost state**, so exhaustion deletes rather than leaving a zero. Counted in publishes, not wall-clock — a timer would expire while the admin is still sorting out channel permissions and the boost would silently do nothing. Seeded by the backend from `Guilds.registerNewGuild` **only** (see [ADR 0012](./docs/adr/0012-onboarding-boost-queue-priority.md) for why not `Channels.add`); the proxy reads it at enqueue and `DECR`s on a boosted publish. Reads **fail closed** — a fail-open Redis blip would promote the whole base to the boosted tier at once. Outranks paying guilds deliberately: 10 publishes per new guild costs Premium nothing measurable and this is the window that decides whether a server keeps the bot. See [[Queue priority tiers]].
- **Queue priority tiers** — `BOOSTED = 1`, `NORMAL = 10` on the crosspost queue; lower is higher priority (BullMQ's valid range is `1..2_097_152`). Only two tiers today, spaced to leave headroom. Consuming the [[Onboarding boost]] budget is gated on the job's own `opts.priority`, never on a fresh budget read — an unconditional `DECR` would mint a negative key for every guild in the system.

## Allowlist / registration model

- **Registered channel** — a channel a user opted into auto-publishing via `/ap enable`. Persisted in Postgres `channels` table and mirrored in `Channels` Redis cache (`channel:{id}` keys, value = `{filters, filterMode}` JSON, no TTL).
- **Candidate channel** — an announcement channel offered in the dashboard as an enable-able option. Sourced **live from Discord** (`GET /guilds/:id/channels`, filtered to `GuildAnnouncement`), NOT from the DB — this list is what "appears in the dashboard". Each candidate carries an `enabled` flag = whether a serving [[Registered channel]] row exists (a [[Paused channel]] reads `enabled: false`). Distinct from a registered channel: a candidate can exist with no DB row (never enabled), and a registered row can outlive its candidate (channel deleted in Discord). Cached ≤5 min ([[Dashboard read caching]]) but actively evicted when the bot sees a channel created / deleted / cross the announcement-type boundary, so membership changes surface without the TTL wait.
- **Migrated guild** — a guild that has opted into the v7 allowlist model. Source of truth: `guild.migratedAt` in Postgres (`NULL` = legacy); the `MigratedGuilds` Redis DB (`migrated_guild:{guildId}` = '1', no TTL) is a derived hot-path cache rebuilt at startup. Set on first `/ap enable` or new guild join. Migrated guilds enforce the allowlist; legacy (unmigrated) guilds auto-publish all announcement channels. Migration state is temporary — column and Redis DB are dropped together ~6 months after v7 ships.
- **Bot presence** — record of "the bot is in this guild": `bot_presence` table, pk `guildId`, `leftAt IS NULL` = in guild. Unrelated to Discord's _user_ presence (online status). Replaces the old `guild.deletedAt` semantics (ADR 0006); collapsed from a per-edition composite key by [ADR 0013](./docs/adr/0013-single-bot-one-queue.md). Drives the dashboard's `botPresent` flag and the `BOT_NOT_PRESENT` guard. Kept honest by the nightly reconciliation sweep.
- **Plan** — a guild's tier, free or premium, resolved from its subscription by `Plans.isPremium` (self-host: always premium, there is no billing). A property of the **guild**, never of a running process: one bot serves both, so nothing in the bot, proxy or `@ap/config` branches on it. Replaces the old "managing edition", which meant "which of the two bots is doing the work" — a question that no longer exists. `Plans.reconcileChannelServing` is the single choke point that moves a guild's channels when its plan changes, and the only writer of the [[Queue priority tiers|premium queue marker]].
- **Channel-limit rejection** — hitting the per-guild channel cap on enable/migrate has exactly one cause now: the guild is on the free plan. Surfaced as `code: LIMIT_FREE` on the 400 with an "Upgrade to Premium" CTA. Kept as a named `ChannelLimitReason` type with one member because both clients must branch on the **code**, not the status — `NOT_ANNOUNCEMENT_CHANNEL` is the other 400 from these routes, and rendering it as "you hit your channel limit" is the bug the type prevents.
- **Plan change** — what used to be a handover is now a Redis write and a channel trim. An entitlement grant reactivates every paused row; a revocation pauses the guild to the free shape (filtered channels, then the newest excess beyond the cap). Both run through `Plans.reconcileChannelServing`, driven by the Paddle webhook in **both** directions — on an upgrade that webhook is the *whole* activation path, since nothing joins the guild to trigger it instead. Nothing is invited, nothing leaves, and there is no pending state to nag about. See [ADR 0013](./docs/adr/0013-single-bot-one-queue.md).
- **Soft-deleted presence** — kick/leave sets `bot_presence.leftAt` instead of cascading; all guild-scoped config (channels, filters, `migratedAt`, subscription) survives, so an accidental kick + re-invite restores everything (the derived Redis state is rebuilt from DB, entries first, marker last). On re-invite the bot sends the live announcement-channel list from the GUILD_CREATE payload so config for channels deleted while it was away is pruned (missed `channelDelete` events would otherwise leave stale rows consuming free-plan limit slots). A guild with no active presence rows is purge-eligible 30 days after its newest `leftAt` (reconciliation cron, cutoff-guarded so a re-invite landing mid-sweep wins). Mirrors the billing rule "subscription outlives the guild row."
- **Paused channel** — a registered channel that is retained but not currently served, because its guild is on the free plan and the channel is either beyond the free limit or carries [[Filter|publishing rules]]. "Paused" = _system-paused_, distinct from a user unregistering a channel (which still hard-deletes the row) and distinct from the subscription-scoped `paused` billing status (different entity: a channel is paused, a subscription is paused). Soft-pause via `channel.pausedAt` (nullable timestamp, mirrors `bot_presence.leftAt`): serving iff `pausedAt IS NULL`. **`pausedAt` is set by exactly one thing — the system trim; never by any UI/bot action.** Paused rows keep all config (filters, filterMode) but are absent from the `Channels` Redis allowlist and are NOT counted by the per-guild limit — so the limit counts _serving_ channels, not raw rows. **Purely a backend retention mechanism — there is no picker/swap UX.** In the dashboard a paused channel appears in the ordinary Disabled list (`enabled` = row exists AND `pausedAt IS NULL`), carrying only a subtle muted "Saved setup" tag; enabling it is the normal register-or-unpause path (quietly restores its filters, cap-gated), and toggling it off is the normal destructive delete. So a user who _touches_ a paused channel (enable→disable) deletes it for good and it will NOT return on re-subscribe — retention protects only channels left untouched after downgrade. Never hard-deleted on downgrade (would violate "restore on re-subscribe"). Real orphans are reaped elsewhere: `channelDelete` removes rows for deleted Discord channels, and the 30-day guild purge cascades all rows once the bot has left — so no time-based paused-channel cleanup exists (a timer would only ever delete live, restorable config). **Two reasons a channel pauses, and the second is the load-bearing one:** over the cap, and *filtered*. Filters are premium-only and there is no longer a premium instance whose absence stops them running, so a downgraded guild's filtered channels would otherwise start publishing exactly what an admin filtered out — unrecoverable, where not publishing is not. Enforcement is **billing-driven**: `Plans.reconcileChannelServing` on the subscription webhook, plus a join, a dashboard self-heal, and a state-based nightly backstop (serving-count > 3 → trim if free, mass-action guarded). ADR 0009 chose the old free-join rail over the Paddle path; ADR 0013 reversed that, because a plan change is now the only thing that can break the invariant.
- **Filter** — premium-only message filter (keyword/mention/author/webhook, negatable conditions combined by an any/all match mode) attached to a registered channel. Evaluated bot-side per message before fire-to-proxy, over the whole message text (content + embeds + Components V2). Filter data lives in the `Channels` cache JSON value. **The hot path does no plan check**: a free guild's filtered channels are [[Paused channel|paused]], so they never reach the allowlist — a serving channel with conditions is by construction a premium guild's.
- **Publish permissions** — the exact channel permissions a bot needs to crosspost: `ViewChannel` (baseline) + `SendMessages` + `ManageMessages`. Discord's crosspost endpoint requires Send (own messages) plus Manage (others'); `ReadMessageHistory` is NOT required. Canonical definition is `PUBLISH_PERMISSION_FLAGS` in `@ap/utils`, shared by the bot hot path, the bot `/ap` commands, and the backend gate — one source so the three can't drift (they previously checked 2 / 4 / 3 perms respectively).
- **Publish-state cache** — per-channel `{ canPublish, missing[] }` derived from the [[Publish permissions]], **computed by the bot** off its gateway cache (zero Discord REST) and pushed to the backend on the permission events it already handles (`channelUpdate` / `guildMemberUpdate` for `members.me` / `roleUpdate`, batched per guild) plus a full sweep on shard `ready` / `guildCreate`. Stored in a per-guild Redis hash (`publish_state:{guildId}`, DB 13, 14-day safety TTL, fields keyed by `channelId`); the dashboard reads it instead of computing permissions via REST. `BotPermissions.getPublishMap` (backend REST) survives only as a write-back fallback when a channel's field is missing. The bot is the source of truth; a Redis flush self-heals on the next sweep. See [ADR 0008](./docs/adr/0008-bot-pushed-publish-state.md).

## Billing (Paddle)

- **Paddle** — merchant of record and payment processor for premium subscriptions. See [ADR 0004](./docs/adr/0004-paddle-merchant-of-record.md).
- **Subscription source of truth** — Postgres `subscription` table in this repo's backend, updated by Paddle webhooks. Redis is a possible derived cache, never the owner.
- **Checkout** — a **single unified checkout surface** at the public `/checkout` route, running Paddle's **overlay** (see the Default payment link entry). The backend creates the Paddle transaction (price items + server-set `custom_data: {discord_guild_id, discord_user_id}`, duplicate-subscription guard) and returns the transaction ID; the in-app upgrade flow (subscription panel) then **navigates** to `/checkout?_ptxn={id}&g={guildName}&icon={url}` — the same page every Paddle-sent link lands on — and that page opens the overlay. custom*data is server-set, never client-set (`g`/`icon` are cosmetic only — they orient the page sitting behind the overlay — and are never a trust boundary; the overlay owns the authoritative line items, tax, grand total and renewal terms). **No price, plan or trial flag is passed**, deliberately: a query string is customer-editable, so anything the page stated about price could contradict the overlay in front of it. Requires a client-side token in web and live-domain approval in Paddle. **Overlay, not inline, is deliberate**: Paddle obliges the \_integrating page* to reproduce a description of what's being purchased, subtotal/tax/grand total with currency, the recurrence cadence and renewal total, the full frame including Paddle's footer, and a refund-policy link whenever it uses **inline** mode — and `/checkout` rendered none of that while it was inline. The overlay renders all of it itself ("unlike inline checkout, your page does not need to render any of this separately"), so delegating keeps the disclosures correct and current with Paddle's compliance changes instead of mirroring them by hand. **Field collection is entirely Paddle-owned** — no customer PII stored locally (MoR boundary, ADR 0004). Paddle collects the minimum (email + country) by default. **The transaction is created WITHOUT a `customerId`** so the checkout always runs its collection step; pre-binding a customer with a complete address skips collection entirely (dropped deliberately). Paddle re-links repeat buyers by the email they enter (different email splits them — accepted). No way to force customer-name capture on a plain consumer checkout (accepted — Paddle owns invoice compliance). **Settings passed to `Checkout.open()` are ignored when a `transactionId` is supplied** — so all checkout behaviour (`displayMode: 'overlay'`, `theme: 'dark'`, `showAddTaxId`) lives in the Initialize block (`apps/web/src/lib/paddle.ts`, via `usePaddle({ onCompleted })`; the hook still accepts a `settings` override that nothing uses, kept for a future per-route need). On `checkout.completed` the page redirects to `/dashboard/{guildId}/overview?success=true` (guild id from `custom_data`) — the [[Overview banner stack]]'s checkout-activation card takes over: it **polls for the webhook-written subscription** (`hasSubscription`) and self-resolves into the premium-invite banner it hands off to, so the "activating…" state can never dead-end waiting on the webhook. Paddle's success screen skipped.
- **Default payment link (`/checkout`)** — Paddle's single configured URL and the app's **one unified checkout surface**. Every customer-facing Paddle link decorates it with `?_ptxn={transactionId}`: abandoned-checkout recovery (`_paction=recovery`), past-due payment-method-update/dunning links (Paddle Retain), and any API-generated `checkout.url`; the **in-app upgrade flow** targets it too (panel navigates to `/checkout?_ptxn={id}&g={guildName}&icon={url}`). Hosted at a dedicated **public** route (never the marketing homepage). The page loads Paddle.js (`initializePaddle`) with the app-wide overlay settings and calls **`Checkout.open({ transactionId })` imperatively** — _not_ Paddle.js's load-time `?_ptxn` auto-open, which fires only during the CDN script's initial bootstrap and does **not** re-fire on client-side navigation (`initializePaddle()` on an already-loaded instance just updates it), so a second SPA visit — back → upgrade again, or a router-cache restore — would leave nothing open until a hard refresh. Opening on the instance covers every mount: hard load, SPA nav, and Paddle-sent recovery/dunning links alike (we act on `_ptxn` only and ignore `_paction`). **Behind the overlay** the page renders a real card, not a blank screen: "Complete your purchase", a **server indicator** (guild icon + name from `g`/`icon`, in-app flow only — Paddle-sent links get no card) and a **"Go to checkout"** button. It states no price and no plan: see the Checkout entry. That card exists because dismissing an overlay is one keystroke and used to strand the customer on an empty page with no way back; the button re-opens the same transaction (deliberately bypassing the duplicate-open guard, which is keyed per transaction to absorb React re-renders/StrictMode). Non-happy paths: no `_ptxn` → redirect `/`; already-paid/expired txn → Paddle.js renders its own error. On `checkout.completed` we read `custom_data.discord_guild_id` (server-set at transaction creation; surfaces on the event, `CheckoutEventsData.custom_data`) and redirect to `/dashboard/{guildId}/overview?success=true` — the **Overview** tab, where the checkout-activation card lives, not the Subscription tab (the login bump for a logged-out email opener is accepted — fulfillment already happened); absent our IDs (e.g. Retain payment-method transactions) → generic success page. **Fulfillment is webhook-driven regardless — this page is pure funnel UX.** Must be a Paddle-approved domain, configured separately in the sandbox and production Paddle dashboards (default payment link lives under Paddle → Checkout → Checkout Settings).
- **Subscriber** — the Discord user who paid for a guild's subscription (`subscriberDiscordUserId`, sourced from server-set checkout `custom_data`). A permanent, non-transferable billing role, distinct from guild admin: any MANAGE_GUILD user can see subscription status, but only the subscriber controls billing. If the subscriber becomes unreachable via the dashboard (left guild, lost MANAGE_GUILD, deleted account), nobody takes over — Paddle receipt emails carry portal links, so the payer can always cancel; residual cases go to support.
- **Manage Billing** — Paddle Customer Portal session created by the backend on demand, URL returned only to the subscriber (`portalUrl`). No in-app cancel/payment-method UI is built or maintained. Non-subscriber admins see "Billing is managed by @X" instead of the button — the backend resolves the subscriber's username live via proxy `GET /users/:id` (cached in-memory in the backend ~1h, non-fatal fallback to the raw ID). The subscriber sees the button only (no self-attribution); the API response carries an explicit subscriber field so the panel never infers the role from `portalUrl` presence (a failed portal-session call must not demote the subscriber's view).
- **Duplicate subscription guard** — if a second _entitled_ subscription with a different `paddleSubscriptionId` arrives for an already-entitled guild (two admins completed checkout before either webhook landed — the 409 checkout guard only covers transaction creation), `applyPaddleSubscription` keeps the FIRST subscription, ignores the new one, and fires the alert webhook; support cancels+refunds the duplicate in Paddle. Safe because the 409 guard means a legitimate new subscription can only arrive while the existing row is non-entitled (which still overwrites).
- **Entitled** — a guild whose subscription status is `active`, `trialing`, or `past_due`. Local statuses mirror Paddle's five verbatim (`active`, `trialing`, `past_due`, `paused`, `canceled`); `past_due` keeps premium so Paddle dunning can recover the payment. Only `canceled`/`paused` revoke. A stored scheduled change (cancel/pause + effective date) drives "cancels on X" UI.
- **Paddle customer** — the Paddle-side customer entity, resolved by Paddle from the email entered at checkout (one customer per email; one customer can hold subscriptions for multiple guilds). Its ID lands on the subscription row (`paddleCustomerId`) via webhook and is what portal sessions use. Checkout does **not** pre-bind it (see the Checkout entry) — repeat buyers stay one customer only by reusing their email. The Paddle customer `name` is customer-owned and customer-facing (checkout, invoices, portal) — never encode Discord IDs in it; Discord linkage lives in subscription `custom_data`.
- **Plan catalogue** — one Paddle product ("Auto Publisher Premium"), **four** prices: $4.99/month and $49.99/year, plus a duplicate of each carrying `trial_period` 14 days. Amounts are tax-INCLUSIVE, so the quoted price is what the buyer pays in any VAT jurisdiction. The trial belongs to the price, not the checkout, which is what stops conversion from counting as a price change and re-opening the statutory withdrawal window; one trial per guild ever (`Subscriptions.isTrialAvailable`). Beyond Paddle refunds there is now a statutory withdrawal function (ZZP čl. 81.a / CRD Art 11a) with a mandatory full refund — see `services/withdrawal.ts`. Price IDs are backend-only config (backend creates the transaction); the only browser-side Paddle value is `PADDLE_CLIENT_TOKEN`, served at runtime — there are no `NEXT_PUBLIC_*` variables anywhere in the repo.
- **Subscription outlives the guild row** — `subscription` has no cascading FK to `guilds`. Kicking the bot or deleting the server never deletes or cancels the subscription (kick is often accidental; re-invite restores premium instantly). The subscriber cancels via dashboard/portal; the dashboard can show a subscription for a server the bot is no longer in.
- **No per-transaction invoicing export** — the old HMAC invoicing forwarder (`invoicing.ts`) is deleted. Paddle (MoR) issues customer invoices; company bookkeeping runs off Paddle payout statements.
- **Revocation** — a `canceled`/`paused` webhook makes the backend trim the guild to the free shape via `Plans.reconcileChannelServing`. **Nothing leaves the guild**: one bot serves both plans, so losing Premium changes what it publishes, not where it is (ADR 0013 — this is what deleted `Discord.leaveGuild`, the presence-gating that avoided a pointless `DELETE /users/@me/guilds/:id`, and the whole invalid-request-budget argument around it). Idempotent, so the webhook and the nightly backstop can both call it. The **grant** direction runs through the same call and is now the entire activation path — no join event will do it instead. Backstopped by `getRevokedWithBotPresent` (not entitled, bot still present) in the subscription reconcile, mass-action guarded in the revoke direction only: un-pausing a guild's own channels is never destructive, so grants apply inline and unguarded. A daily reconciliation cron lists subscriptions from the Paddle API and repairs Postgres drift (missed webhooks); it replaces the hourly local `currentPeriodEndsAt` expiry scan — Paddle owns period-end cancellation.

## Dashboard

- **Guild Overview tab** — the guild dashboard's **attention surface** and default landing tab: `/dashboard/:guildId` redirects to `/overview` (was `/channels`), so opening a guild shows banners + status first. Hosts the guild-scoped banner stack (moved off the shell — see [[Overview banner stack]]) plus a read-only **channel status** section. Status is **permission-derived from existing data only** (the [[Publish-state cache]], ADR 0008) — no publish-activity feed or rate-limit counters are plumbed to the web. Migrated guild: itemized list, each enabled channel shown as _publishing_ (`canPublish === true`), _needs permissions_ (`canPublish === false`), or _paused_ (`hasSavedSetup`), under a four-state **channel-status header** (see below); the list is **read-only** (no toggles — Channels tab stays the sole place to enable/disable) and is **regrouped by health** (`statusRank` in `channel-status.tsx`): broken (`canPublish === false`) first, then healthy — with Discord [[Sidebar order]] preserved _within_ each group (a stable sort over the backend's pre-sorted array). The Overview is the attention surface, so severity outranks position here; the Channels tab keeps pure sidebar order, which is why a channel can sit at a different index on the two tabs. Retained/paused rows trail (matching the Channels tab's Disabled column), themselves in sidebar order. Rows are red or green only — the yellow "premium bot lacks access" tier went with the handover (ADR 0013). Each broken row shows the shared [[Channel Fix affordance]] instead of linking to the Channels tab. The **channel-status header** (`channel-status.tsx`) has three precedence-ordered states, driven by _channel publishing health only_ — deliberately decoupled from the [[Overview attention badge]] count so an unrelated banner (paused) no longer demotes it: **Welcome** (`enabled === 0 && paused === 0` → blue "Ready to get started?", steer to the Channels tab; the rare downgraded-then-emptied `enabled === 0 && paused > 0` falls through here too), **Issues** (`needsFixingCount > 0` → red "N channels aren't publishing", "grant the missing permissions — see the list below"), and **All good** (`enabled > 0`, no red → green "Publishing in N channels"). **Paused channels never affect the header** — excluded from every state and from the "All good" count (their sole purpose is preserving setup for a later re-upgrade; they surface only as muted trailing rows + the dismissible paused banner, never as a header nag). Legacy guild: **no itemized list** — just a minimal "publishing in N of M channels" summary under a prominent migrate banner (steer to migrate before per-channel detail). A small **persistent info callout** in the status header states Discord's 10-published-messages/hour/channel limit (informational only — we surface no live counter). **`/ap overview` is the Discord mirror of this surface** (renamed from `/ap status`, whose optional `channel` argument was dropped — the list already names every registered channel and the exact permissions to grant, and `/ap filters` covers per-channel detail, so the per-channel branch earned nothing) — same broken-first regrouping over the same [[Sidebar order]], same per-row `✓ Publishing` / `✕ Not publishing` labels, same header copy ("N channels aren't publishing" + "grant the missing permissions" vs. "All good" + "Publishing in N channels"), and paused rows trailing. It mirrors the legacy branch too: a legacy guild gets the same non-itemized "publishing in N of M" summary rather than per-channel detail (previously it hit the empty state and claimed nothing was enabled — legacy guilds have no channel rows, so the backend's `/guild/:id/channels` now also returns `migrated`, read from Postgres `guild.migratedAt` rather than the fail-closed `MigratedGuilds` cache). The Welcome state splits on whether the guild has any announcement channels at all (counted from the bot's own channel cache), and the downgraded-then-emptied case keeps its paused rows instead of early-returning. One deliberate divergence: no per-row Fix button (Components V2 caps components per message), so the Fix modal's permission instructions are inlined once below the list and a single `Open dashboard` link button closes every reply. The list is one joined string in a single Text Display — 1 component regardless of channel count — and truncates at 25 rows (10 paused) with an overflow line, since a hydrated app emoji costs ~32 of the message's 4000 characters; the broken-first sort guarantees truncation only drops healthy rows. Its `canPublish` is the same cache-only View+Send+Manage check the [[Publish-state cache]] feeds the dashboard, so the two surfaces report identical okay/not-okay states.
- **Overview banner stack** — all guild-scoped banners render **only inside the Overview tab**; the shell and the other guild tabs render no guild-level banners. Order (top → bottom): (0) **checkout activation** (query-param-scoped on `?success=true`, set by the post-checkout redirect to `/dashboard/:guildId/overview?success=true`) — a **self-resolving, phased** card, not a static confirmation. Armed only when `?success=true && !hasSubscription`; while pending it shows a neutral "Checkout complete! Activating… this page updates automatically" card (**never "payment received"** — a trial checkout completes at $0.00) and **polls via `router.refresh()` every 3s** (soft RSC re-fetch → re-seeds the guild list → `hasSubscription` observes the webhook write live from Postgres; no client fetch, per ADR 0007). On activation it stops and shows a one-time green "Premium is now active" card. There is nothing to hand off to and no next step for the admin: the webhook un-pauses the guild's channels in place (ADR 0013). At a **60s ceiling** still-inactive it hard-stops to a calm fallback card ("activation is taking longer than usual") with a manual Refresh button + support link. Bounded, one-time, post-checkout only; refreshes are mostly warm (guild-list Discord read 60s-cached, guild detail 5min-cached). (1) **misconfigured channels** (red, non-dismissible; migrated guilds where `needsFixingCount > 0` — ≥1 _enabled_ channel with `canPublish === false`; copy: "Some channels aren't publishing … see the channel list below to fix them" — placed first among the warnings as the only _current outage_), (2) **legacy migration** (amber, → migrate modal), (3) **paused channels** (yellow, dismissible). The premium-invite and premium-pending banners are **deleted** — upgrading no longer moves a guild between bots, so neither state exists. Banners 0–2 stay non-dismissible; paused stays the lone dismissible exception (episode-scoped `localStorage` marker per `guildId`, ADR 0009). Off-tab, the only persistent signal is the [[Overview attention badge]].
- **Overview attention badge** — a count on the Overview sidebar item, visible on **every tab within a guild's dashboard** (computed client-side in the shell from `useGuild()` context — zero new data; scoped to the guild dashboard, NOT the server-list page, whose payload lacks channel-level `canPublish`). Counts **one per active banner** only (misconfigured channels, legacy migration, and paused **only while not dismissed**); the positive checkout-activation card never counts. **Broken channels tally as one, not per-channel** — any number of _enabled_ channels with `canPublish === false` collapse into the single red [[Overview banner stack|misconfigured-channels banner]] (= 1), so five broken channels add 1, not 5. The per-channel [[Channel Fix affordance]] and the channel-status header's "N aren't publishing" counter are presentational only and never bump this badge (banner-driven). Legacy guilds have no misconfigured banner (migration comes first). Badge hidden entirely at 0. It is the mitigation for banners no longer nagging on every page.
- **Channel Fix affordance** — one shared button + modal that surfaces a channel's publish problem identically on the [[Guild Overview tab]] and the Channels tab (the plan's "same Fix buttons and same modals"). - **Dashboard read caching** — the dashboard is Discord-REST-bound, not DB-bound, so caching lives in two layers, never in the query layer (ADR 0007). (1) **Backend in-memory** `cachedGet(route)` over the three per-guild bot-scoped GETs (`/guilds/:id/channels`, `/roles`, `/members/:botId`), **keyed by route only** (5-min TTL, in-memory not Redis — single-instance backend, TTL self-evicts). `/channels` and `/roles` are guild-global (Discord returns all regardless of the fetching bot's perms), so one entry per guild; only 200s cached. Retires `LegacyGuildPerms` (the `canPublish` map recomputes free from the cached raw roles+member). The composed `/api/guild/:guildId` still reads Postgres/Redis live, so web mutations reflect instantly. (2) **Web** — no cross-request cache. The guild payload is **not** cached in the shared Next.js Data Cache: `/api/guild/:guildId` authorization is per-user and enforced in the backend (`requireGuildPermission`, `MANAGE_GUILD`, 60s-cached per token), so a shared server cache in front of it would bypass authz and expose a guild to any logged-in user — every guild load hits the backend and authz runs each time. Warm loads are fast anyway (Lever B serves Discord data; the authz check is 60s-cached). Invalidation is TTL-only for **permission** data (roles / bot member / `canPublish`) — no permission-ping eviction (would burn the REST budget in high-churn guilds). The **channel list** is the one exception: actively evicted when the bot sees a channel created / deleted / cross the `GuildAnnouncement` type boundary, so a new [[Candidate channel]] appears (and a deleted one disappears) without the 5-min wait — a narrow, low-frequency trigger, deliberately NOT routed through the high-churn permission-sync path (ADR 0007 amendment). Everything edited in the dashboard reflects instantly (live Postgres/Redis reads); only Discord-derived permission data is ≤5 min stale. Instant back-navigation to an already-opened guild comes from Next.js's client Router Cache (`experimental.staleTimes.dynamic = 60`, per-browser, busted by the mutations' existing `router.refresh()`) — not a client-caching library. **Guild-list read (`GET /api/user/guilds`)**: reads through its own 60s per-token `DiscordAuth` cache (previously write-only — it warmed the entry for `requireGuildPermission` but re-fetched Discord every call); presence/subscription are still composed live from Postgres, so only the raw user-token `/users/@me/guilds` call is skipped when warm. **Presence self-heal is guild-scoped, not fleet-wide**: the eager per-guild `isBotInGuild` fan-out over every managed guild in the list endpoint is removed (it re-confirmed permanent absences every 30s, O(admin-guild-count) member-fetches per load, all 404s that don't count toward the CF budget but waste proxy throughput/latency). Heal now fires **only on the guild resource** (`GET /api/guild/:guildId`, which already self-heals the one guild it serves and whose `requireGuildPermission` + botless-throw own authz _and_ presence gating — so the `[guildId]` layout no longer fetches the guild list to gate), and **premium heal is entitlement-gated** (skip the premium member-fetch unless the guild is entitled — a non-entitled guild's only "present" outcome is the revocation leave, already owned by the nightly reconcile). **Switcher/sidebar chrome** reads from a persistent client-side guild-list provider (hoisted to the `dashboard` layout, **seeded by RSC** — no browser-facing backend route, no token in the browser) so it does not blank behind the shell `<Suspense>` skeleton on guild-to-guild navigation; the list refreshes on the existing `router.refresh()` + window focus. A full client-side data-fetch migration (SWR/React Query) stays rejected (ADR 0007): direct browser→backend fetch would expose `BACKEND_URL` + require a browser-held credential (DDoS/token attack surface), and the BFF-route alternative is a net complexity add, not a reduction.
- **Sidebar order** — the dashboard channels list mirrors Discord's sidebar, not the raw API response (`GET /guilds/:id/channels` is unordered, and `position` is scoped per category — two channels in different categories can share a position): uncategorized channels first, then categories by their position, channels within a category by `position`, ties by snowflake id ascending (Discord's own tiebreak). Sorted backend-side in `GET /api/guild/:guildId` where the full channel list (incl. categories) is in hand before the announcement-type filter drops them — the API contract is "channels arrive in sidebar order"; the web only preserves array order (enabled/disabled sections each stay internally ordered). No category labels in the UI. The ordering rule itself lives in exactly one place — `sortBySidebarOrder` in `@ap/utils`, an accessor-based sort so the backend can hand it raw `APIChannel`s and the bot discord.js channels without either shape leaking into the other. **`/ap overview` is ordered too** (it no longer "stays unordered"): the backend's `/guild/:id/channels` returns ids in DB order, so the bot re-derives the sidebar order from its own channel cache (`rawPosition` + `parentId`, incl. categories) — free, no REST call, no position data on the wire. Channels the bot can't resolve (deleted, or no ViewChannel so they never entered the cache) have no position; they sink past their group, still tiebroken by id, so the order stays deterministic rather than input-dependent.

## Web auth

- **Session vs. Discord token** — two independent lifetimes the web must reconcile. The NextAuth session is a JWT with rolling `maxAge: 3d` (re-issued on activity → alive indefinitely for frequent visitors); the Discord OAuth **access token** embedded in it is captured **once** at sign-in (`if (account)` in `auth.ts`) and expires **7d** later. There is no refresh-token rotation ([[Reactive re-login]] handles the gap instead). Session config is deliberately left untouched — changing `maxAge` would mass-log-out everyone on deploy, and reactive re-login reconciles the mismatch by construction.
- **Reactive re-login** — the web's response to a dead Discord token: any `401` from a backend read/mutation means "session dead" → transparently re-login (no refresh rotation). `backendFetch` maps every 401 to a single `AuthExpiredError` (safe: `/api/*` is behind `createDiscordAuth`, which only 401s on a bad token; `requireGuildPermission` returns 403). Handled at three seams anchored on that error: (1) **RSC reads** — the top `dashboard` layout (`GuildListLoader`) catches it → renders `<AuthRedirect>` (same handling as the existing session-missing check; the choke point every full load passes through); (2) **streamed guild-detail promise** — `[guildId]` layout `.catch`-maps it to a typed `{ authExpired: true }` sentinel the shell reads (thrown errors are sanitized across the RSC→client boundary in prod, so identity can't be relied on — return a typed value instead); (3) **server-action mutations** — the existing `{ ok: false, status }` result, with a shared client helper firing `signIn` on `status === 401`. Re-login **is** the cleanup: `signIn('discord')` round-trips with no consent prompt (scopes `identify guilds` unchanged) and the `jwt` callback overwrites the dead token — no cookie-clearing route needed. Refresh-token rotation was rejected (single-use-token multi-tab logout race for a ~weekly no-consent redirect); revocation 401s regardless, so reactive re-login is required either way. See [ADR 0010](./docs/adr/0010-web-auth-expiry-reactive-relogin.md).

## Ops

- **Alert webhook** — Discord webhook (`DISCORD_ALERT_WEBHOOK_URL`) for events where a human should act, sent via a fire-and-forget `sendAlert(key, ...)` helper in a dedicated `@ap/alerts` package (send failure only logs, never fatal; `@ap/logger` stays Redis-free). ## Services

- **bot** — discord.js gateway listener, one instance serving every guild on either [[Plan]]. Multi-shard via discord-hybrid-sharding. Owns no Discord REST traffic on the hot path (gates everything synchronously, fires-and-forgets to the proxy). Does sync permission checks against discord.js cache (never `.fetch()`). Knows nothing about a guild's plan: it reads `premium` off `GET /guild/:id/channels` for the slash commands, and never on the publish path.
- **backend** — internal Express API, single instance (ADR 0006). Owns channel registration, filter CRUD, Paddle subscriptions, bot presence, [[Plan]] resolution and the channel-serving trim, guild migration markers, the public `/api/*` web surface, and the `Channels` Redis cache. One `@discordjs/rest` client through the proxy. It is the **only** thing that knows a guild's plan — and the only writer of the [[Queue priority tiers|premium queue marker]].
- **proxy** — see Crosspost pipeline above; one instance, with a pinned egress IP. Discord's invalid-request ceiling is per **IP**, so that pin is the whole of the ban mitigation — the old per-edition IP split protected against a token-scoped ban that does not exist (ADR 0013).
- **web** — Next.js dashboard. Reads from the single backend's `/api/*` (one `BACKEND_URL`).

## Key architectural rules

- **Be conservative with Discord REST calls — always.** The hard ceiling is the Cloudflare invalid-request ban (10k 401/403/non-shared-429 per 10 min per egress IP; proxy self-sheds at 5k), and several routes are per-token/per-user rate-limited to 1/window. Treat every Discord REST call as scarce budget: dedup calls (never fetch the same resource twice in one request), prefer cache/DB-derived state, gate calls behind presence/relevance checks so no call is made when the answer is already known, and never add speculative or polling calls. When designing a feature, the default question is "can this avoid a Discord call?" — see ADR 0007 (dashboard caching favours TTL over active eviction for exactly this reason) and the `Revocation` entry (leaves are presence-gated to avoid pointless 429-generating calls).
- **Bot never `.fetch()`s on the hot path.** `members.me` is auto-populated by `GUILD_CREATE`; trust the cache. Permission checks use `permissionsFor` only.
- **Bot's REST = proxy's REST.** Bot's discord.js is configured with `api: '{proxy}/api'` (`config.proxyUrl`) and `globalRequestsPerSecond: Infinity` (proxy is the global limiter).
- **Crossposts are never dropped on transient errors.** Route 429s are absorbed by discord.js internally. Sublimit (long waits), global 429s, 5xx, and network errors all become BullMQ delayed retries. Only `already_done`, `blocked`, `sublimit-lock`, and `fatal_4xx` are intentional skips.
- **Single REST instance per token.** One `@discordjs/rest` handles crosspost queue worker and `/api/*` passthrough. Global ceiling is `50/s`; interactions use `BurstHandler` so they don't compete with crossposts.
- **Every `queue.add` passes an explicit priority.** BullMQ serves un-prioritized jobs **before** prioritized ones — `fetchNextJob.lua` `RPOPLPUSH`es from the `wait` list and only falls back to the prioritized sorted set when `wait` is empty, and `priority: 0` means "no priority". So a single untagged `queue.add` starves every boosted guild behind a backlog that at peak never drains, making the [[Onboarding boost]] strictly worse than plain FIFO. Use a [[Queue priority tiers]] constant, never a bare `queue.add`. Regression check: `bull:crosspost:wait` must stay empty under load while `bull:crosspost:prioritized` carries the depth. See [ADR 0012](./docs/adr/0012-onboarding-boost-queue-priority.md).
